# One linked folder, one project

An external linked folder remains a single working project, such as an existing website.
Linking adds its pointer; shared knowledge stays in the original GTM OS brain. Do not scaffold
a second brain, workspace hierarchy or subprojects in that external folder.

When the person asks to organize several projects or build that kind of structure there,
propose separate folders directly inside the existing GTM OS workspace and follow
[New Project](../../gtm-os-project/SKILL.md). Resolve the location from the brain root,
not this chat's folder. For example, from an external Website project linked to FDE OS,
propose `FDE OS/research/` for a new Research project, not `Website/research/`.
When redirecting an explicit request for a subfolder here, ask one `configuration_question`
naming the proposed absolute destination inside the brain workspace and capture scope,
with Create project / Cancel. Wait for the submitted choice before `link_project`; the
original request for a nested location does not approve this different destination. Reuse
only a submitted choice that already approves that same destination and capture scope.
Do not silently move, copy, unlink or reorganize the existing project.

Keep the GTM OS project layout flat: a project cannot contain another linked project or
be linked inside one, including through a path alias or a nested repository. A refusal is
not a reason to create the folders or pointers by hand. Existing nested registrations are
not automatically migrated; propose separate locations when the person wants to change them.

This boundary concerns GTM OS organization. Existing application directories such as `src/`,
`assets/` and `tests/` remain ordinary project files, not separate GTM OS projects. Preserve
them and support normal application work; do not flatten an existing repository or register
its implementation directories as projects.

## Lane S2: workflow triggers, milestones and limits
Today a workflow is a document in workflows/ with type: workflow and three headings (Before starting, Steps, Learn); a run is notes in one context, one per step, with the due date; only a person starts one; steps are free text (see WORKFLOWS.md, scripts/gtm-brain-workflow, the two shipped drafts in templates/workflows, and test/live/demo-loops.mjs).
Owner's decisions: a skill is one sitting of work; a workflow is skills in sequence with gates between steps; a person, a schedule or a save starts it; one skill with a trigger is the shortest workflow; each step ends on a completion milestone the brain can see, reaching it is saved as a note and that note starts the next step; rules bind every step; no owner field on a workflow.
Build:
- A checked header on a workflow file: status (draft, active, paused), trigger (manual; a schedule such as "every Monday 09:00" or "daily"; or a brain event: a note saved about a kind, a link of a type created or ended, a field changed, a field missing for N days), and what it reads and writes (kinds, links, fields, tool categories). Existing files without a header keep working as manual drafts.
- Steps: each step may name a skill (by its name) or keep an inline description; each has a gate (after N days, on a date, when a named milestone is reached) and a milestone that is observable (a note with a tag, a link created, a field filled, a document written). A step with no observable milestone is reported when the workflow is checked.
- Declarations for skills: a small "needs" block a skill can carry (kinds, links, fields, tool categories). Add it to the shipped skills where it is clear what they need. Switching a workflow or a skill on compares its needs with the brain's SCHEMA.md and connected tools and returns one proposal listing what is missing; it does not change the schema itself (that goes through the existing schema path with the person's yes).
- A check before a workflow can be active: header valid, every kind, link and field exists in the schema, every named skill exists, every step has a milestone, no other active workflow on exactly the same trigger; and a dry run on one real example that lists what it would read and write, without writing.
- Events: the write path emits events (a note saved about a kind, a link created or ended, a field changed); matching active workflows are offered at the next chat start in one line each, never run silently. Schedules are evaluated at chat start and by the existing background run. The same event starts a workflow once (recorded as the run's first note, so a second chat or a teammate's machine sees it is taken).
- Runs: state is only the chain of notes. Continuation: a step is due when its gate has passed and the previous milestone note exists. A milestone not reached by its date raises the step again, once a day at most.
- Limits with safe defaults in one place: active runs per workflow, steps a day, a chain of workflows starting each other stops at depth 3, a workflow's own notes never trigger itself, one setting turns all workflows off. A failed step stops the run and says why.
- Reads for people: a "workflows" view in query (per workflow: status, trigger, each run's step, what it waits for and until when, last result) and the commands to pause, resume, cancel a run, skip a step and move a date, all recorded as notes.
- A schema change (a kind, link or field removed or renamed) flags and pauses the workflows that name it.
